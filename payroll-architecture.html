§00 · Alignment

تصمیمات کلیدی معماری — قبل از هر چیز

این موتور روی یک ERP زنده (سپتا) پیاده می‌شود که خودش قبلاً چند تصمیم معماری گرفته. به‌جای ساخت یک جزیره‌ی جدا، این طراحی عمداً از زیرساخت موجود استفاده می‌کند تا سیستم منسجم بماند.

♻️ RBAC از قبل وجود دارد

permissions / permission_groups در سپتا از قبل ساخته شده. نقش‌های HR Manager / Payroll Expert / Finance Manager / CEO / Viewer به‌صورت گروه‌های دسترسی پیش‌فرض جدید ساخته می‌شوند — نه یک سیستم نقش موازی.

♻️ زیرساخت تولید سند از قبل وجود دارد

ماژول proposal-documents (HTML→PDF با Puppeteer، Excel با ExcelJS، بارکد با bwip-js) دقیقاً همان چیزی است که فیش حقوقی نیاز دارد. پیشنهاد: تعمیم آن به یک documents module مشترک، نه بازسازی از صفر.

⚠️ تداخل با جداول Payroll فعلی

جداول ساده‌ی فعلی (payroll_periods, payslips) هاردکد و بدون نسخه‌بندی‌اند. این موتور آن‌ها را جایگزین می‌کند، نه تکمیل. جزئیات مسیر مهاجرت در §00-الف.

⚠️ تداخل با کارکرد ماه (WorkLog)

جداول attendance_records, overtime_records, leave_requests, mission_requests از قبل وجود دارند. PayrollWorkLog باید یک Snapshot تجمیعی خودکار از این‌ها باشد، نه ورود دستی موازی. جزئیات در §00-ب.

§00-الف — تصمیم مورد نیاز: سرنوشت payroll_periods / payslips فعلی

§01 · System Architecture

معماری سیستم

معماری Layered + Pipeline: کنترلرها فقط HTTP را ترجمه می‌کنند، سرویس‌ها فقط orchestration انجام می‌دهند، و تمام محاسبات داخل Engine‌ها و Pipeline Stage‌ها اتفاق می‌افتد. هیچ Business Logic در Controller/Service نیست.

  • هیچ محاسبه‌ای در Controller/Service نیست — سرویس‌ها فقط بار را از Repository می‌گیرند و به Engine مربوطه تحویل می‌دهند.
  • Engine‌ها Stateless و Pure هستند — ورودی می‌گیرند، خروجی برمی‌گردانند؛ بدون side-effect پنهان، تست‌پذیر با Unit Test ساده.
  • Repository Pattern بین Prisma و Service قرار می‌گیرد — سرویس‌ها هیچ‌وقت مستقیم prisma.xxx.findMany صدا نمی‌زنند.
  • Accounting Integration فقط از طریق Interface — هیچ وابستگی مستقیمی به نرم‌افزار حسابداری خاصی وجود ندارد (رجوع به §01 پایین).

§03 · Database

طراحی دیتابیس و Prisma Schema

همه‌ی جدول‌ها از الگوی سپتا پیروی می‌کنند: PK از نوع UUID (gen_random_uuid())، نام‌گذاری snake_case در دیتابیس، و created_at روی جدول‌های اصلی. نسخه‌بندی (PayrollRuleVersion) ستون فقرات کل طراحی است.

prisma/schema.prisma — payroll domain13 models
model PayrollYear {
  id           String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  yearNumber   Int      @unique @map("year_number")
  calendarType String   @default("jalali") @map("calendar_type") // jalali | gregorian
  status       String   @default("open")  // open | closed
  createdAt    DateTime @default(now()) @map("created_at")

  ruleVersions PayrollRuleVersion[]
  periods      PayrollPeriod[]

  @@map("payroll_years")
}

model PayrollRuleVersion {
  id            String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  payrollYearId String    @map("payroll_year_id") @db.Uuid
  versionNumber Int       @map("version_number")
  title         String                                  // "1406 Version 1"
  effectiveFrom DateTime  @map("effective_from") @db.Date
  effectiveTo   DateTime? @map("effective_to") @db.Date
  status        String    @default("draft") // draft | active | superseded
  createdById   String?   @map("created_by") @db.Uuid
  createdAt     DateTime  @default(now()) @map("created_at")

  payrollYear PayrollYear         @relation(fields: [payrollYearId], references: [id])
  rules       PayrollRule[]
  brackets    PayrollTaxBracket[]
  formulas    Formula[]
  periods     PayrollPeriod[]

  @@unique([payrollYearId, versionNumber])
  @@map("payroll_rule_versions")
}

model PayrollRule {
  id            String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  ruleVersionId String    @map("rule_version_id") @db.Uuid
  code          String    // MIN_WAGE, HOUSING_ALLOWANCE, INSURANCE_RATE_EMPLOYEE, INSURANCE_CEILING, ...
  title         String
  valueType     String    @map("value_type") // number | percent | boolean
  value         Decimal   @db.Decimal(18, 4)
  effectiveDate DateTime  @map("effective_date") @db.Date
  expireDate    DateTime? @map("expire_date") @db.Date
  description   String?
  createdAt     DateTime  @default(now()) @map("created_at")

  ruleVersion PayrollRuleVersion @relation(fields: [ruleVersionId], references: [id])

  @@unique([ruleVersionId, code])
  @@map("payroll_rules")
}

// پله‌های مالیات پلکانی — چون ذاتاً چندردیفی است، در قالب Rule عمومی جا نمی‌شود
model PayrollTaxBracket {
  id            String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  ruleVersionId String   @map("rule_version_id") @db.Uuid
  bracketOrder  Int      @map("bracket_order")
  fromAmount    Decimal  @map("from_amount") @db.Decimal(18, 4)
  toAmount      Decimal? @map("to_amount") @db.Decimal(18, 4) // null = آخرین پله، بدون سقف
  ratePercent   Decimal  @map("rate_percent") @db.Decimal(5, 2)

  ruleVersion PayrollRuleVersion @relation(fields: [ruleVersionId], references: [id])

  @@unique([ruleVersionId, bracketOrder])
  @@map("payroll_tax_brackets")
}

model Formula {
  id            String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  ruleVersionId String   @map("rule_version_id") @db.Uuid
  code          String
  expression    String   @db.Text  // "BASE + HOUSE + FOOD" یا "IF(CHILDREN>0, CHILDREN*CHILD_ALLOWANCE, 0)"
  description   String?
  createdAt     DateTime @default(now()) @map("created_at")

  ruleVersion PayrollRuleVersion @relation(fields: [ruleVersionId], references: [id])
  components  PayrollComponent[]

  @@unique([ruleVersionId, code])
  @@map("payroll_formulas")
}

model PayrollComponent {
  id            String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  code          String   @unique // BASE, HOUSE, FOOD, CHILD, SENIORITY, OVERTIME, NIGHT, HOLIDAY, BONUS, INSURANCE, TAX, LOAN, ADVANCE, OTHER
  title         String
  componentType String   @map("component_type") // earning | deduction
  isInsurable   Boolean  @default(false) @map("is_insurable")
  isTaxable     Boolean  @default(false) @map("is_taxable")
  calcOrder     Int      @default(0) @map("calc_order") // راهنمای نمایش؛ ترتیب واقعی از Dependency Engine می‌آید
  formulaId     String?  @map("formula_id") @db.Uuid
  status        String   @default("active")
  createdAt     DateTime @default(now()) @map("created_at")

  formula     Formula?            @relation(fields: [formulaId], references: [id])
  resultItems PayrollResultItem[]

  @@map("payroll_components")
}

model PayrollPeriod {

§06 · Rule Engine

طراحی Rule Engine

مسئولیت این Engine فقط بارگذاری است، نه محاسبه. ورودی: سال + تاریخ اجرا (یا شناسه‌ی نسخه‌ی مستقیم). خروجی: نقشه‌ای از code → value که بقیه‌ی Engine‌ها مصرف می‌کنند.

interface RuleSet {
  ruleVersionId: string;
  values: Record<string, number>;      // MIN_WAGE -> 7113000000
  brackets: TaxBracket[];
}

class RuleLoader {
  // یک نسخه‌ی فعال دقیقاً برای هر بازه‌ی زمانی وجود دارد؛ همپوشانی effectiveFrom/effectiveTo رد می‌شود
  async loadByPeriod(periodId: string): Promise<RuleSet>
  async loadByVersion(ruleVersionId: string): Promise<RuleSet>
  async loadByDate(entityCalendarType: 'jalali'|'gregorian', date: Date): Promise<RuleSet>

  • نتیجه‌ی بارگذاری Cache می‌شود (کلید = ruleVersionId) — چون یک نسخه پس از استفاده در هر دوره‌ی «بسته‌شده» عملاً Immutable است.
  • اگر برای یک تاریخ هیچ نسخه‌ی فعالی پیدا نشود → خطای صریح NoActiveRuleVersionError، نه مقدار پیش‌فرض ساکت.

§07 · Formula Engine

طراحی Formula Engine — بدون eval

یک Recursive-Descent Parser دستی که متن فرمول را به AST تبدیل می‌کند، سپس یک Evaluator جدا AST را با یک Context اجرا می‌کند. هیچ‌جا از eval یا new Function استفاده نمی‌شود.

گرامر (EBNF)

expression   := logicalOr
logicalOr    := logicalAnd ( "OR" logicalAnd )*
logicalAnd   := comparison ( "AND" comparison )*
comparison   := additive ( ("=="|"!="|">"|">="|"<"|"<=") additive )?
additive     := multiplicative ( ("+"|"-") multiplicative )*
multiplicative := unary ( ("*"|"/"|"%") unary )*
unary        := ("-"|"!")? primary
primary      := NUMBER | IDENTIFIER | call | "(" expression ")"
call         := IDENTIFIER "(" ( expression ("," expression)* )? ")"

// توابع پیش‌ساخته: IF(cond,then,else) MIN(...) MAX(...) ROUND(v,d?) FLOOR(v) CEIL(v) ABS(v) PERCENT(v,p)

AST + Evaluator (Type-Safe)

§10 · Insurance Engine

طراحی Insurance Engine

interface InsuranceResult {
  employeeShare: number; employerShare: number; unemploymentShare: number; total: number;
  insuranceBase: number; // بعد از اعمال سقف
}

class InsuranceEngineService {
  calculate(insurableBase: number, rules: RuleSet): InsuranceResult {
    const base = Math.min(insurableBase, rules.values['INSURANCE_CEILING']);
    const employeeShare = base * rules.values['INSURANCE_RATE_EMPLOYEE'] / 100;
    const employerShare = base * rules.values['INSURANCE_RATE_EMPLOYER'] / 100;
    const unemploymentShare = base * rules.values['UNEMPLOYMENT_RATE'] / 100;
    return { employeeShare, employerShare, unemploymentShare, total: employeeShare+employerShare+unemploymentShare, insuranceBase: base };
  }
}

ورودی مبنای بیمه = مجموع Component‌هایی که isInsurable=true دارند (از خروجی مرحله‌ی ۵). تمام نرخ‌ها و سقف از RuleSet می‌آیند — تغییر سالانه فقط یعنی رکورد جدید در PayrollRule.

§11 · Tax Engine

طراحی Tax Engine — مالیات پلکانی

class TaxEngineService {
  calculate(taxableIncome: number, rules: RuleSet): number {
    const exemption = rules.values['TAX_EXEMPTION'] ?? 0;
    let remaining = Math.max(0, taxableIncome - exemption);
    let tax = 0;
    for (const b of rules.brackets.sort((a, b) => a.order - b.order)) {
      const bandSize = (b.toAmount ?? Infinity) - b.fromAmount;
      const taxableInBand = Math.min(remaining, bandSize);
      if (taxableInBand <= 0) break;
      tax += taxableInBand * b.ratePercent / 100;
      remaining -= taxableInBand;
    }
    return tax;
  }
}

درآمد مشمول مالیات = مجموع Component‌های isTaxable=true منهای معافیت و کسورات قابل کسر (مثلاً سهم بیمه‌ی کارگر، طبق قانون). پله‌ها در PayrollTaxBracket نگه داشته می‌شوند تا افزودن/حذف پله بدون تغییر کد ممکن باشد.

Defense in Depth

گارد Service-Layer کافی نیست چون قابل‌دور زدن با یک باگ آینده است. پیشنهاد: یک Postgres Trigger روی payroll_results که هر UPDATE را وقتی status='locked' است رد کند — دقیقاً مثل رفتار فعلی سپتا در قفل‌کردن مرحله‌ی «انتخاب نهایی» استعلام‌ها، اما این‌بار در سطح دیتابیس.

نسخه‌بندی و بازمحاسبه‌ی تاریخی

هر PayrollPeriod به یک ruleVersionId ثابت اشاره دارد. اگر سال ۱۴۰۷ قانون عوض شود، یک PayrollRuleVersion جدید ساخته می‌شود؛ دوره‌ی فروردین ۱۴۰۶ همچنان به نسخه‌ی قدیمی اشاره می‌کند، پس بازمحاسبه‌ی آن (حتی سال‌ها بعد) دقیقاً همان اعداد سابق را تولید می‌کند.

§18 · Risks & Roadmap

ریسک‌ها، نقاط باز و پیشنهادهای آینده

  • عملکرد Batch: اجرای هم‌زمان صدها کارمند نیاز به موازی‌سازی محدود (p-limit) دارد؛ برای مقیاس خیلی بزرگ‌تر، صف پیام (BullMQ) در نظر گرفته شود.
  • Formula Builder بصری: فاز اول فقط ورود متنی فرمول؛ یک ادیتور بصری (Block-Based) نقطه‌ی توسعه‌ی طبیعی آینده است.
  • حسابداری دوطرفه: Accounting Integration فعلاً فقط یک سند تولید می‌کند؛ یکپارچگی کامل دفتر کل خارج از اسکوپ این فاز است (دقیقاً هم‌راستا با یادداشت موجود پروژه درباره‌ی ماژول حسابداری آینده).
  • تعدیل معوقه (Arrears): اصلاح فیش یک دوره‌ی Locked باید به‌صورت یک ردیف تعدیل در دوره‌ی جاری مدل شود، نه بازنویسی گذشته — نیاز به طراحی جداگانه.
  • دو تصمیم باز §00-الف/ب باید قبل از شروع پیاده‌سازی نهایی شوند.
